Architecture

From pixels to torques.

A single observation graph feeds both the planners and the learned policies. The same interfaces serve simulation and the real robot.

01
Unified observation graph

Head RGB-D, two wrist cameras, joint encoders, LiDAR, and IMU are time-synchronized into a single ROS 2 message graph. Every consumer — MoveIt2, Nav2, or a policy — reads from the same source of truth.

02
Policy & planner side by side

Learned policies emit action chunks at 10–30 Hz; classical planners (MoveIt2, Nav2) handle collision-aware motion and global routing. A small arbiter decides which authority owns each actuator group at any moment.

03
Sim-parity interfaces

The same topic names and message types drive the MuJoCo / Isaac twin and the hardware driver, so a policy trained in sim deploys with no glue code. See Simulation.

04
Data engine built in

Every teleop and autonomous episode streams to HDF5 / Zarr — images, joint states, actions, and goals — directly into the learning pipeline. See Learning.

Buses & I/O

Talking to every joint.

Fifty-one actuators, a dozen sensors, one real-time loop. Here's how the bytes move.

01
Real-time actuator bus

Quasi-direct-drive motors run on CAN FD; swerve and wrists ride RS-485. Torque goes down, encoder and current come back — 200 Hz+, fast enough for gravity comp and impedance.

02
Synchronized cameras

A head RGB-D and two eye-in-hand wrist cameras are hardware-timestamped, so images and joint states line up to the millisecond before a policy ever sees them.

03
One clock, one graph

Cameras, encoders, LiDAR, and IMU share a time base and publish into one ROS 2 graph — no skew between what MABEL sees and where it thinks it is.

04
Deterministic loop

C++ firmware on the microcontrollers holds the hard real-time edge; the Jetson closes the control loop at a fixed rate. See Hardware for the wiring.

Mapping & SLAM

Two maps, one world.

ROS gmapping turns the 2D LiDAR into a clean occupancy grid for fast, reliable planning. A visual 3D SLAM layer fuses the RGB-D cameras into a dense 3D map with loop closure — so MABEL localizes by what it sees, not just what it bumps into.

gmapping (2D)Visual 3D SLAMLoop closure
01
Localization

Scan-matching and AMCL on the 2D grid, corrected by visual loop closures — MABEL holds its pose down long, repetitive corridors.

02
Nav2 navigation stack

A global planner finds the route; a local controller tracks it while dodging obstacles. Costmaps fuse LiDAR and depth; recovery behaviors handle the dead ends.

03
Holonomic by default

Nav2 is configured for an omnidirectional footprint, so the swerve base strafes and rotates as one — through doorways, around islands, into elevators.

04
Building-scale

Pre-built floorplans with live SLAM correction carry MABEL across rooms and floors — the backbone of the long-horizon demos.

Modules

Composable by design.

01

Drivers

200 Hz CAN/RS-485 actuator drivers for swerve, arms, and ORCA hands — publish /joint_states, subscribe to commands.

02

Calibration

Automated encoder-offset and kinematic calibration on first boot; differential wrist mapping handled in software.

03

Navigation

SLAM Toolbox mapping with Nav2 configured for a holonomic footprint — strafe and rotate planned as one.

04

Whole-body control

A QP-based controller resolves base, lift, torso, and arm redundancy against task and posture objectives.

05

Policy runtime

A thin PyTorch inference server runs Diffusion Policy / ACT checkpoints with normalization stats bundled in.

06

Recorder

Lossless episode logging to HDF5 / Zarr, ALOHA/ACT-compatible, with per-frame camera and action alignment.
