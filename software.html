L1 · Firmware

Close to the metal.

Each actuated subsystem runs its own microcontroller firmware — deterministic loops down at the bus level, with a clean command/feedback contract up to ROS.

01
Swerve base

Teensy firmware (PlatformIO) drives the three swerve modules over the REV CAN protocol — six brushless motors, drive plus steer. Ships with a Python GUI and a drive sim; setup_can.sh brings up and enumerates the bus.

02
Arms

PlatformIO (C++) firmware runs the OpenArm-derived 7-DOF arms — quasi-direct-drive motors on CAN FD, fast enough for gravity compensation and impedance control.

03
ORCA hands

The 17-DOF tendon-driven ORCA hands run on Dynamixel / Feetech servos through the orca_core driver, exposing per-joint position feedback to the host.

04
Head & lift

A 3-DOF Dynamixel neck (pan / tilt / roll) is driven from the Dynamixel SDK; the linear lift column runs its own MCU firmware with a host-side GUI for setup and homing.

L2 · ROS 2

One graph, every joint.

A single ROS 2 Humble workspace (mabel_ws) wraps every firmware target behind standard topics. One launch file brings up the whole robot.

01
Hardware drivers

mabel_base_hardware, mabel_arms_hardware, mabel_body_hardware, and mabel_orca_hand bridge each firmware bus to ROS — publishing /joint_states, subscribing to commands at 200 Hz+.

02
Sensors & time base

mabel_sensors brings up the head RGB-D, two eye-in-hand wrist cameras, and the base 2-D LiDAR — hardware-timestamped onto one clock so images, scans, and joint states line up to the millisecond.

03
Description & interfaces

mabel_description holds the URDF, meshes, and RViz config — the same kinematic tree used in sim. mabel_interfaces defines the custom messages and services the stack speaks.

04
One-command bringup

ros2 launch mabel_bringup robot.launch.py starts the full stack — base, arms, hands, sensors, and description — over DDS. The same topic names drive the MuJoCo / Isaac twin, so there's no glue code between sim and real.

L3 · Navigation

Knows where it is.

Map the space with the base's own sensors, localize within it, and plan a holonomic path through it — building-scale, all onboard.

SLAM map · occupancy grid + RGB-D cloud
Mapping & SLAM

Built from the base up.

The base 2-D LiDAR feeds SLAM Toolbox (mabel_slam), turning raw scans into a clean occupancy grid with loop closure for fast, reliable planning. The onboard RGB-D cameras add a dense visual layer — so MABEL maps and localizes by what it senses, not just what it bumps into.

SLAM Toolbox2-D LiDARRGB-DLoop closure
01
Localization

Scan-matching against the LiDAR grid, corrected by visual loop closures from the base cameras — MABEL holds its pose down long, repetitive corridors.

02
Nav2 stack

mabel_navigation runs Nav2: a global planner finds the route, a local controller tracks it while dodging obstacles. Costmaps fuse LiDAR and depth; recovery behaviors handle the dead ends.

03
Holonomic by default

Nav2 is configured for an omnidirectional footprint, so the swerve base strafes and rotates as one — through doorways, around islands, into elevators.

04
Building-scale

Pre-built floorplans with live SLAM correction carry MABEL across rooms and floors — long-horizon mobility for whole-body manipulation tasks.

L4 · Software

From pixels to torques.

Above ROS sits the application layer — perception, motion planning, and whole-body control. A single observation graph serves every consumer, in sim and on the real robot alike.

01
Unified observation graph

Head RGB-D, two wrist cameras, joint encoders, LiDAR, and IMU are time-synchronized into one ROS 2 message graph. MoveIt2, Nav2, and the whole-body controller all read from the same source of truth.

02
Whole-body control

A QP-based controller resolves base, lift, torso, and arm redundancy against task and posture objectives — bimanual motion and the mobile base planned as one system. See Whole-Body Control.

03
Collision-aware planning

MoveIt2 handles collision-checked motion for the arms and torso; a small arbiter decides which authority — planner or controller — owns each actuator group at any moment.

04
Sim-parity interfaces

The same topic names and message types drive the MuJoCo / Isaac twin and the hardware driver, so behavior validated in sim deploys with no glue code. See Simulation.
