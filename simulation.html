Overview / Simulation
The digital twin

A robot you can
break for free.

MABEL exists twice. One copy is aluminium and 59 motors; the other is a 2 ms MuJoCo timestep, and both answer to the same controller through the same wire contract. Every trajectory, every policy and every bug is cheaper to find on the second one — so that is where the work starts.

One model

The twin is the same robot.

There is one file. simulation/mabel_mujoco/models/mabel_full.xml is the canonical MABEL — 67 generalized coordinates, 59 actuators, 9 cameras, 370 sensors — and the ROS URDF, the web GLB you have been orbiting, the headset rigs and the controller’s tip-over constants are all generated from it. Nothing on this site was modelled twice.

01

Edit the MJCF

Geometry, inertia, joint limits — one file, one place.

02

Re-run the chain

MJCF → URDF → GLB → app rigs → mirror, in order. Each step eats the last step’s output.

03

Never edit the output

A hand-edited URDF survives until the next regeneration, then silently does not.

The plant

One process owns
the physics.

On the robot, hardware_bridge is the only thing that opens a device. In simulation, simulation_bridge is the only thing that calls mj_step. Same rule, same seam — which is why the teleop server, ROS, the cameras and every viewer are clients either way, and why the launch flag use_sim:=true is the whole difference.

The scene library

Thirty-five places
to get it wrong.

A robot that only works in an empty room works in an empty room. The scene library is 35 released worlds that <include> the canonical model — homes, kitchens, cafes, warehouses, streets — each a registry entry in scenes.json with its own XML, thumbnail and category. Renderers & engines

Physics is the authority.
Pixels are negotiable.

Three simulators live in the tree, and they are not competing. MuJoCo owns time and contact; the other two change what the cameras see, or what steps the world, without changing a single byte of the contract the apps and ROS speak.

MuJoCo

The default, and the truth

Headless, 500 Hz, elliptic friction cone with 3 noslip iterations. This is the plant every number on this site was measured against.

simulation/mabel_mujoco/

Unity

Photoreal sensors

MuJoCo still steps the world; Unity (URP, Metal) renders it and simulates the cameras and lidar. The prime directive is that ROS, the teleop apps and a policy cannot tell — same topics, rates, intrinsics and TF.

simulation/mabel_unity_sim/

Genesis

A second physics backbone

Swaps MuJoCo out for the Genesis engine while keeping every client-facing wire contract byte-compatible, so the iOS, web and Vision Pro clients connect unchanged.

simulation/mabel_gensis_world/

Not released as a build target. Unity and Genesis are working branches of the simulation stack, not part of the reproduction path. Build MABEL against MuJoCo; the install chapter covers that one.
Data collection in simulation

Episodes that don’t
know they’re fake.

Teleoperate the twin and the collector writes exactly the file it writes on hardware: one HDF5 per episode, axis 0 = frame at 15 Hz. Because the format is identical, a dataset can mix simulated and real episodes, and the trainer never learns which is which.

In every episode_XXXX.h5What it holds
camerasJPEG blobs, one group per camera
planar lidarthe same scan the RPLIDAR produces
per-actuatorjoint_pos / vel / torque, all 59
generalized stateqpos / qvel, plus body poses and base twist
action/ctrlthe training label — a 59-vector of absolute joint targets, not deltas
schema_jsonactuator names and order, camera list, units — so nothing downstream hard-codes them

Reinforcement learning

Learning from reward,
4096 at a time.

Imitation learning needs a human to show it. The RL track needs nobody — it needs a GPU and a reward. MABEL’s dexterous-manipulation environments run on a vendored fork of mjlab (Isaac-Lab’s manager-based API on MuJoCo-Warp), with PPO and thousands of parallel worlds on one card.

01

No RL model file exists

The environment is derived from the canonical MJCF at load time — build_manip_spec prunes the lidar and tendons, deletes base_root for a fixed pedestal, and adds grasp sites. Edit the MJCF and the change simply arrives.

02

Training is GPU-only

MuJoCo-Warp on macOS can build, reset, step and run the test suite, but not the PPO update. A Mac is for evaluation and CI; PPO wants CUDA.

03

Gains are tuned per group

Position actuators throughout, arms at k_p = 100 and hands at k_p = 2 — a finger tendon and a shoulder do not want the same stiffness.

Run it

Nothing to buy,
nothing to break.

The whole stack — physics, cameras, the teleop gateway and a browser control studio — comes up on a laptop with one script. Phones, headsets and browsers then connect to the twin exactly as they later connect to the robot: same ports, same wire contract, and the clients cannot tell which is live.

cd server && ./run.sh is the whole twin in one command; simulation_bridge can also be run on its own against any scene in the library. Both, with their flags and their prerequisites, are in the wiki’s install chapter.
