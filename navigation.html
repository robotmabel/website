Overview / Navigation
L3 · Navigation

Knows where it is.

MABEL ships two independent SLAM backends and picks one per run: a CPU 2-D LiDAR mapper and a GPU visual stack that reconstructs the room in 3-D. Either one corrects the drift the swerve wheels accumulate — then Nav2 plans a holonomic path through the map. All onboard.

mabel_slam

Two ways to know the world.

One package, two interchangeable backends. The same launch works in sim and on the robot — it auto-detects the clock and the GPU. Pick a backend and watch the map form.

slam_toolbox · 2D occupancy
0 0 corrects map → odom

A 360° laser, a pose graph, a loop closure.

  1. 01
    Scan in

    The base RPLIDAR A3 sweeps 360° and publishes /scan in lidar_link — the same topic in sim and on hardware.

  2. 02
    Scan match → graph

    slam_toolbox matches each scan to the running map and drops a Ceres pose-graph node every 0.2 m / 0.2 rad of travel.

  3. 03
    Loop closure

    Returning near a past pose, it searches an 8 m window and snaps the graph straight — erasing the drift the wheels piled up.

  4. 04
    Occupancy out

    The optimized graph rasterizes to a 5 cm /map, refreshed every 0.5 s. Pure CPU — no GPU needed.

Stereo features for pose, voxels for shape.

  1. 01
    Stereo in

    The front RealSense D435i IR pair streams 848×480 @ 15 Hz; a ZED Mini head cam swaps in for tabletop detail.

  2. 02
    cuVSLAM

    NVIDIA's GPU stereo VSLAM tracks features frame-to-frame and closes loops, correcting map → odom in real time.

  3. 03
    nvblox mesh

    Registered depth integrates a TSDF into a colored 3-D mesh — 5 cm voxels for driving, 1 cm for manipulation.

  4. 04
    2-D slice out

    An ESDF height-slice becomes the same /map — so Nav2 never knows which backend ran.

What it measured

The wheels lie. Vision doesn't.

Against a ground-truth benchmark, the raw swerve odometry over-reads ~3× from wheel slip. cuVSLAM tracks the real path — so the EKF anchors absolute pose to vision and keeps the wheels only for high-rate velocity.

Path planning

Nav2, tuned holonomic.

mabel_navigation runs Nav2 against whichever SLAM map is live — slam:=lidar | visual | none — configured for the omnidirectional swerve base.

01
One map contract

Both backends publish the same /map and the same map→odom→base_link TF chain, so Nav2 consumes either transparently — swap LiDAR for vision without touching a planner param.

02
MPPI controller, Omni model

A NavFn global planner finds the route; an MPPI local controller — set to the Omni motion model — tracks it while sampling around obstacles. Costmaps fuse /map with the live /scan.

03
Holonomic envelope

Speed caps match the teleop limits — vx 0.8, vy 0.7, ω 2.0 — so the swerve base strafes and spins as one through doorways and around islands.

04
EKF-fused odometry

A robot_localization EKF blends cuVSLAM's drift-free pose with the wheels' high-rate velocity — and bridges brief visual dropouts. allow_unknown lets it plan into unmapped space.

Onboard sensing

Everything it needs to navigate, it carries.

01

RPLIDAR A3

A 360° planar scanner on the base feeds slam_toolbox and the live Nav2 obstacle layer over /scan.

02

RealSense D435i

Front stereo-IR + depth drives cuVSLAM and the nvblox mesh — emitter on for dense depth, IMU off (Jetson quirk).

03

ZED Mini

A head stereo camera for fine, 1 cm-voxel reconstruction when MABEL leans in to manipulate.

04

Swerve odometry

Drive + steer encoders give a high-rate velocity prior — drifty alone (~3×), but the EKF's smooth fallback.

05

Isaac ROS · NITROS

cuVSLAM and nvblox share one GPU container with zero-copy buffers; on x86 it auto-runs in Docker.

06

Nav2 costmaps

Static (/map) + obstacle (/scan) + inflation layers, with behavior-tree recoveries for the dead ends.
